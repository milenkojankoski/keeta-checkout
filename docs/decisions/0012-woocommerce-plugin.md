# 0012. The WooCommerce plugin

Date: 2026-10-30
Status: accepted

## Context

Step 11, and the first consumer of the REST contract that is not written in
TypeScript. WooCommerce is where small shops actually are, and unlike Shopify it has
no gatekeeper: write a gateway, merchants install it.

A correction to something said while planning this: the plugin is PHP, so it cannot
reuse the TypeScript SDK. The two are independent, and the SDK was not a
prerequisite.

## Decisions

**Redirect, not an inline form**

1. `process_payment()` creates a session and returns a redirect to `hostedUrl`. The
   pay page already handles the QR, the deep link, the live status and the
   copy-the-details fallback, and it works with JavaScript off. Reimplementing that
   inside a WooCommerce checkout would be worse and would need maintaining twice.
2. The order moves to `on-hold`, not `pending`, because the customer has committed
   to a payment method and the stock should be held while they pay.

**The browser never confirms a payment**

3. The webhook completes the order. A browser can be closed, scripted, or lied to.
4. **But** `woocommerce_thankyou_` also reads the session back from the server when
   a customer returns to an unpaid order. The webhook usually arrives first; this
   closes the window when it has not, without trusting the browser, because the
   answer comes from the checkout server rather than from the fact that somebody
   loaded a URL.

**Three things in the webhook handler that are not optional**

5. **The raw body.** `WP_REST_Request::get_body()` returns what arrived;
   `get_json_params()` returns a re-decoded structure whose spacing and key order
   differ, and which therefore cannot verify. Noted in the file, because this is
   the mistake every webhook integration makes once.
6. **`hash_equals`.** A `===` on an HMAC leaks, through timing, how many leading
   bytes were right.
7. **Dedupe on `event.id`,** kept in order meta. Delivery is at-least-once, so a
   retry after a timeout must not complete an order twice.

**A forged order id cannot complete the wrong order**

8. The handler matches the order id *and* then checks the session id stored on that
   order. Without the second check, a correctly signed event for session A carrying
   order B's id would complete order B.

**The currency trap**

9. The checkout server performs **no** conversion: it charges the number given, in
   the token given. A EUR store configured with `$USDC` would charge the wrong
   amount by the exchange rate. The settings screen checks the pairing against a
   known table and warns. It warns rather than blocks, because a merchant may
   deliberately treat a stablecoin as 1:1.

**The amount normaliser refuses rather than guesses**

10. WooCommerce's own formatting helpers take a decimal-places argument and will
    round to it. Rounding what somebody owes is not a formatting decision, so the
    plugin normalises the total itself with no rounding anywhere and lets the server
    reject anything it cannot represent exactly.
11. It handles what a WooCommerce install actually produces: dot decimals, comma
    decimals, both grouping conventions, floats, and leading or trailing separators.
    **Anything ambiguous is refused.**

## The bug worth recording

The first version of the normaliser stripped any repeated separator as grouping. So
`1.2.3` became `123`, and `1,2,3` became `123`: nonsense input silently turned into
a charge a hundred times too large. The test suite caught it on the first run.

Grouping now has to be *shaped* like grouping, one to three digits then groups of
exactly three, and a single comma followed by exactly three digits is refused
outright because `1,234` is either 1234 or 1.234 and there is no way to tell. Two or
four digits after a comma is unambiguous, since grouping is always three, so those
are still accepted.

A second, smaller bug in the same run: `normalise(0)` returned `"0"` because the
integer fast path skipped the zero check.

## Verification, and its limits

There is no PHP or WordPress on this machine, so the plugin runs in a `php:8.3-cli`
container:

- every file passes `php -l`;
- **122 assertions pass** in `plugins/woocommerce/tests/run-tests.php`, which needs
  neither PHPUnit nor WordPress;
- **12 of those are cross-language fixtures**: signatures generated by the server's
  own TypeScript `signWebhook` and verified by the PHP implementation, including
  unicode, a `</script>` sequence, the U+2028 line terminators, escaped quotes, a
  5 KB body, and five deliberately invalid cases that must be refused. The PHP
  signer also has to reproduce each header byte for byte. Two implementations of an
  HMAC scheme that were never checked against each other is how a webhook
  integration silently rejects every delivery.

Regenerate the fixtures with `pnpm fixtures`; run the PHP suite with
`pnpm test:php`, which needs Docker.

### Verified in real WordPress, 2026-10-31

`plugins/woocommerce/dev/` brings up WordPress 7.1.4, WooCommerce 11.2.1, MariaDB
and a Keeta Checkout server built from this repository, with the plugin bind-mounted
from the working tree. One `docker compose up -d` installs and configures all of it.

A complete payment went through it:

| Step | Result |
| --- | --- |
| gateway registration | `WC_Gateway_Keeta_Checkout`, available, configured |
| `process_payment()` | created a session, order moved to `on-hold` |
| the redirect | `http://localhost:3000/pay/cs_…` |
| a real send on the test network | 0.01 KTA from the dev payer wallet |
| the webhook | delivered on the first attempt, HTTP 200 |
| the order | `processing`, `is_paid`, transaction id set to the block hash |
| the order notes | the amount, the payer and the explorer link |

The security-critical paths were probed directly against the live endpoint:

| Probe | Answer |
| --- | --- |
| replay of a handled event | 200 `duplicate: true`, nothing changed |
| a new event id for an order already paid | 200, not re-completed |
| the right order id with the wrong session id | 200 `matched: false`, refused |
| a tampered body | **400 NO_MATCH** |
| the wrong secret | **400 NO_MATCH** |
| no signature header | **400 MALFORMED_HEADER** |
| an unknown order | 200 `matched: false` |

After all of that the paid order was still `processing`, still had its original
transaction id, and still had exactly one settlement note.

**What is still not verified:** the settings screen and its warnings have only been
read, not clicked through, and no payment has gone through the WooCommerce checkout
form in a browser as a shopper would. The gateway's own code path has, through
`process_payment()`.

### Four bugs the WordPress run found

1. **The Docker image had never actually built.** There was no `.dockerignore`, so
   `COPY . .` dropped the host's `node_modules`, built for another platform and full
   of pnpm symlinks, on top of the tree the image had just installed. pnpm then
   tried to purge it and refused without a TTY. Step 9 claimed a working image on
   the strength of the files existing.
2. **`pnpm prune --prod` produced a container that died on its first import.** It
   leaves packages in the store but strips the per-package symlinks, so
   `packages/cli/node_modules` was empty and `@keetanetwork/keetanet-client` could
   not be resolved. Replaced with `pnpm deploy`, which assembles a self-contained
   tree.
3. **Two workspace projects were both named `keeta-checkout`,** the root and the
   CLI, which made `pnpm --filter=keeta-checkout deploy` ambiguous and is a latent
   hazard for every other filtered command. The root is now
   `keeta-checkout-workspace`.
4. **The plugin claimed WordPress 6.4 and WooCommerce 9.4.** WooCommerce 11.2.1
   requires WordPress 7.0, so the stated floor was a configuration the plugin cannot
   run in. Corrected to 7.0 and 9.0, tested against 7.1 and 11.2.

One more thing the run surfaced that is not a bug: **WooCommerce stores prices at
two decimals by default**, so a 0.001 product became 0.00 and the gateway correctly
refused to create a session for a zero total. The dev shop prices its test item at
0.01 instead. Worth knowing for anyone pricing in a token where small amounts
matter.

## Consequences

- `pnpm fixtures` and `pnpm test:php` are new scripts. The PHP suite is not part of
  `pnpm test`, because it needs Docker and CI does not have PHP configured yet.
- Per the standing rule in README section 13, the signature verification and the
  order-state transitions want a Fable review before release, since they touch
  payment state.
- The plugin assumes one receiving account per shop, which matches one checkout
  server per shop.
